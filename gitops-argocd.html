Why GitOps exists

Traditional push

CI → kubectl/helm → Cluster

CI needs deployment logic and cluster credentials. Manual changes create unrecorded drift.

GitOps pull

Git ← controller → Cluster

Git declares the desired state. An in-cluster controller compares and reconciles it with the live state.

The four practical ideas

1. Declarative

Describe the end state, not imperative steps.

2. Versioned

Git stores reviewable, auditable desired state.

3. Reconciled

A controller continuously compares desired and actual state.

4. Pulled

The delivery controller fetches and applies changes instead of CI directly driving the cluster.

Lab 1: Does the AppProject let this Application deploy?

The team-a project only allows repos under team-a, destination namespaces matching team-a-*, no cluster-scoped resources, and blocks ResourceQuota. The default project allows everything.

AppProject YAML

apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: team-a
  namespace: argocd
spec:
  description: Team A applications
  sourceRepos:
    - https://example.invalid/team-a/*
  destinations:
    - server: https://kubernetes.default.svc
      namespace: team-a-*
  clusterResourceWhitelist: []          # no cluster-scoped resources
  namespaceResourceBlacklist:
    - group: ""
      kind: ResourceQuota
  roles:
    - name: deployer
      description: Can view and sync, cannot delete
      policies:
        - p, proj:team-a:deployer, applications, get, team-a/*, allow
        - p, proj:team-a:deployer, applications, sync, team-a/*, allow
      groups:
        - team-a-developers
The default project is permissive. Every Application that doesn't name a project lands in default, which allows any source repo, any destination and any resource kind. For multi-team use, create restricted projects and don't use default for real workloads.
Project fieldRestricts
sourceReposWhich Git/Helm/OCI sources Applications may use
destinationsWhich clusters and namespaces they may deploy into
clusterResourceWhitelist / BlacklistWhich cluster-scoped kinds (ClusterRole, Namespace, CRD...) are allowed or denied
namespaceResourceWhitelist / BlacklistWhich namespaced kinds are allowed or denied
rolesProject-scoped permissions, mapped to SSO groups or tokens
syncWindowsWhen syncs are allowed or denied (for example no prod syncs on Friday evening)
orphanedResourcesWarn about resources in the namespace that no Application manages

Central model
One Argo CD manages several destination clusters. Operations are centralized, but credentials and blast radius require strong boundaries.
Per-cluster model
Each cluster has its own Argo CD. Isolation improves, while upgrades, config and observability become distributed.
Promotion
Promote by updating versioned desired state through environments, rather than running an imperative deploy command against each cluster.


Secret strategies
Sealed Secrets
Commit an encrypted custom resource; a cluster controller creates the Secret.
External Secrets
Commit a reference; a controller reads a secret manager and creates/refreshes Secret objects.
SOPS
Commit encrypted files and decrypt only in an authorized delivery workflow.
Vault plugin
Resolve placeholders from Vault during manifest generation.
Never commit: plaintext passwords, tokens, kubeconfigs, private keys, cloud credentials or raw production Secret values. Base64 is encoding, not encryption.

Diagnostic decision tree
Select a symptom.
Systematic method
  1. Confirm the Application source, revision, path/chart, destination and project.
  2. Refresh and inspect conditions, sync status, health status and operation result.
  3. Render expected manifests locally with the same Helm/Kustomize inputs.
  4. Use app diff to identify exactly which field/object differs.
  5. Inspect repo-server for fetch/render failures and application-controller for compare/sync failures.
  6. Inspect the Kubernetes resource, events, rollout and admission-policy response.
  7. Only add ignore rules after proving that the difference is expected and safe.


Rollback means changing desired state
Recommended GitOps rollback
Revert or create a new Git commit that restores a known-good desired state. Review, merge, then reconcile.
Argo CD history rollback
Can restore an earlier deployed revision, but reconcile your Git source as well so Git and live state do not fight.
