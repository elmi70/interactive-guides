🔑 Symmetric encryption: one key, two copies

Like a house key: you and your friend each have an identical copy. The same key locks and unlocks.

This toy is a Caesar cipher: only 25 keys, so the hacker wins instantly. Real symmetric ciphers like AES-256 have 2256 possible keys, far too many to try in the lifetime of the universe. Same idea, much bigger key.

⚠️ The catch: how does Bob get the key?

If Alice sends the key over the network, the hacker copies it and reads everything. Sharing the key safely is the problem asymmetric encryption solves (next tab).

openssl enc -aes-256-cbc -pbkdf2 -salt -in secret.txt -out secret.enc   # encrypt
openssl enc -d -aes-256-cbc -pbkdf2 -in secret.enc -out decrypted.txt   # decrypt with the SAME password

✍️ The other direction: signatures

Flip it around: sign with the private key, verify with the public key. Only the owner could have made the signature, and anyone can check it. This is what certificates and TLS handshakes use to prove identity.

GoalWho uses 🔓 publicWho uses 🔑 private
Confidentiality (encrypt)Sender encryptsReceiver decrypts
Identity (sign)Anyone verifiesOwner signs

⏳ One year later: the server's private key is stolen!

The hacker recorded today's traffic. Can they decrypt it now?

This is forward secrecy. In TLS 1.3, server.key only signs. The session key comes from temporary ECDHE keys that are thrown away, so old recordings stay safe.
curl -v https://www.microsoft.com -o /dev/null          # watch the handshake
openssl s_client -connect www.microsoft.com:443 /dev/null | grep -E "Protocol|Cipher|Server Temp Key"

✅ Your checks

🛂 Passport analogy

The certificate is a passport: public, and anyone can photocopy it. The private key is your face. A stolen passport is useless if the face doesn't match. TLS checks both: a valid CA stamp and proof of the private key (CertificateVerify).

ProblemSolved by
"Am I talking to the real server?"Certificate + proof of private key
"Can anyone read our traffic?"Symmetric encryption with the session key
"What if ca.key is stolen?"❗ Nothing. Keep it offline / in an HSM

🖥️ SSH: every user brings their own key pair

Each user runs ssh-keygen on their own laptop. Only the 🔓 .pub goes to the server. The server has one host key for everybody.

💻 Laptops

🖥️ Server prod-01

Host key (one per server): 🔑 ssh_host_ed25519_key 🔓 .pub
Login order: ① server proves itself with its host key (checked against your ~/.ssh/known_hosts) → ② ECDH agrees a symmetric session key → ③ you sign a challenge with your private key, and the server checks it against authorized_keys → ④ everything encrypted with AES/ChaCha20. Never share a private key between people, because then you can't audit or revoke one person.

📝 Kubelet TLS bootstrapping = the certificate request flow

sudo kubeadm certs check-expiration
openssl x509 -in /etc/kubernetes/pki/apiserver.crt -noout -subject -issuer -ext subjectAltName
openssl verify -CAfile /etc/kubernetes/pki/etcd/ca.crt /etc/kubernetes/pki/etcd/server.crt
kubectl get csr && kubectl certificate approve <csr-name>
