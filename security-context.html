🏢 The Container Building

Security context explained with a giant office building, badges and keycards. From "who is running my container?" to user namespaces and Pod Security. Click, play and explore!

🏢 One building, many floors

Picture one huge office building. Lots of teams rent a floor each, but they all share the same building. The building's rules decide who may work on a floor and what each person may do.

🎯 Analogy. The node's Linux kernel is the building. Each container is one team's floor. A pod is a team that may use several floors together. Everyone shares the same building, so the building's rules (the security context) matter a lot.

🧓 Grown-up term: a container is an ordinary Linux process with an isolated view of files, network and processes. It shares the host kernel. In Kubernetes, securityContext is the block that sets the process's user and groups, capabilities, seccomp and AppArmor/SELinux profiles, filesystem rules and more. The Kubernetes docs define it as "privilege and access control settings for a Pod or Container".

🪪 Badges: who is running the process?

Every worker wears a badge with a number on it. The building only reads numbers, never names.

🎯 Analogy. The UID is the number on the badge. UID 0 is the building manager (root). The name tag ("appuser") is just a label the front desk looks up in a list (/etc/passwd). The GID is the number on the team sticker. The manager can open every door without asking.

Pick a user and see how Linux file permissions treat each file.

🧓 Grown-up terms: the kernel only sees numeric UIDs and GIDs. Names come from /etc/passwd and /etc/group. Root skips normal file-permission checks. That skip is a separate power called CAP_DAC_OVERRIDE (you will meet it in tab 4). By default, root inside a container is also UID 0 on the host. If an attacker breaks out, they arrive as root. Running as a non-root user, or using a user namespace (tab 10), removes most of that risk.

$ id
uid=0(root) gid=0(root) groups=0(root)

🎫 Choosing a badge: Dockerfile and docker run

Two places decide who the container runs as, and one of them wins.

🎯 Analogy. USER in the Dockerfile is the badge printed in the employee's contract. --user is the manager at the door on day one saying "wear this badge instead". The manager's word wins.

Dockerfile
docker run option

🧓 Grown-up terms: if the image has no USER line, the default is root. A numeric USER 1000 works without an account, but the group falls back to root (gid 0), so write USER 1000:1000 to set both. Create the user first, copy files with --chown, then switch with USER.

FROM debian:12-slim
RUN useradd --create-home --uid 1000 appuser
WORKDIR /app
COPY --chown=appuser:appuser . /app
USER 1000:1000
CMD ["./server"]

🛂 Will Kubernetes let this badge in? (runAsNonRoot)

runAsNonRoot: true is the lobby guard who refuses to let the manager's badge in. But the guard can only check numbers.

🧓 Grown-up terms: the kubelet checks runAsNonRoot before it starts the container. If the user is a name from the image (USER appuser), it cannot prove the number is not 0, so it refuses with CreateContainerConfigError. Prefer numeric users (USER 1000) or set runAsUser in the pod.

🔑 Keycards: splitting root into pieces

Root used to mean "can do everything". Linux now splits that power into separate keycards.

🎯 Analogy. The old model was one master key that opens every door. Capabilities replace it with a lanyard of separate keycards: one opens the loading dock, one the server room, one the electrical cabinet. The container runtime gives root a lanyard with 14 safe cards and keeps the dangerous ones back.

Show:

🧓 Grown-up terms: the Linux capability list has 41 entries on a recent kernel (man 7 capabilities). The default set is decided by the container runtime. Docker and containerd grant the same 14. Other runtimes, such as CRI-O, can use a different list, so check the real value with grep Cap /proc/1/status. The risk labels here are a rough teaching guide, not an official score.

🧮 Decode a capability number

Inside a container, grep Cap /proc/1/status prints hex numbers. Each bit is one keycard. Paste one to decode it.

Keycards: 0/41

🧓 Grown-up terms: a process has five capability sets. Bounding (CapBnd) is the ceiling. Permitted (CapPrm) is what it may use. Effective (CapEff) is what is switched on right now and is what the kernel checks. Inheritable (CapInh) and ambient (CapAmb) control what survives execve. A root process gets effective = permitted. A non-root process has its effective set cleared at start unless the program file has file capabilities. That is why CapEff: 0000000000000000 in a non-root container is normal, even if the pod "added" a capability.

kubectl exec web-pod -- grep Cap /proc/1/status
capsh --decode=00000000a80425fb

🚪 The port 80 problem

Listening on a port below 1024 needs NET_BIND_SERVICE. A non-root web server therefore cannot listen on port 80, and adding the capability to a non-root container usually changes nothing (see above). Setting file capabilities with setcap does not rescue you either when allowPrivilegeEscalation: false is set, because no_new_privs stops an execve from gaining privileges (tab 7).

✅ Fix 1: use port 8080

Let the Service map port 80 to the container's 8080.

✅ Fix 2: pod sysctl

net.ipv4.ip_unprivileged_port_start: 0 in spec.securityContext.sysctls (a safe sysctl).

📝 The rule form: securityContext in Kubernetes

Kubernetes writes the badge request on a form for the building's security desk.

🎯 Analogy. The pod-level section is the default for the whole team. The container-level section is a note about one person that overrides the team default.

Show fields at:

🧓 Grown-up terms: spec.securityContext is a PodSecurityContext. spec.containers[].securityContext is a SecurityContext. Container wins when both set the same field. Init and ephemeral containers have their own securityContext too. Host namespace switches (hostNetwork, hostPID, hostIPC, hostUsers) are plain pod spec fields, not part of securityContext. Run kubectl explain pod.spec.securityContext for your version.

🥇 Try it: which UID wins?

Order: container, then pod, then the image. Check it with kubectl exec web-pod -- id.

📋 A complete example

apiVersion: v1
kind: Pod
metadata:
  name: web-pod
spec:
  securityContext:              # pod level: defaults for every container
    runAsUser: 1000
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: ubuntu
    image: ubuntu
    command: ["sleep", "3600"]
    securityContext:            # container level: wins over the pod level
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]
        add: ["NET_BIND_SERVICE"]

In Kubernetes, write capability names without the CAP_ prefix: NET_ADMIN, not CAP_NET_ADMIN.

🚪 The revolving door (privilege escalation)

Some programs are special: when anyone runs them they briefly wear the manager's badge. That is how ping, su and sudo work.

🎯 Analogy. A setuid program is a revolving door that hands a visitor the manager's badge for a minute. allowPrivilegeEscalation: false puts a sign on the door: "no badge upgrades in this building".

🧓 Grown-up terms: allowPrivilegeEscalation directly controls the kernel's no_new_privs flag (inverted). If you do not set it, it defaults to true. With no_new_privs, an execve cannot gain privileges through setuid/setgid bits or file capabilities. It cannot be combined with privileged: true or CAP_SYS_ADMIN, because those are inconsistent with it. The restricted Pod Security level requires false.

🗄️ Locked cabinets and shared drawers (files and volumes)

Can your worker write in the place where the app needs to write? This is the number one reason hardened pods "suddenly break".

🎯 Analogy. readOnlyRootFilesystem locks the cabinets that came with the floor. You still need a drawer you may write in (an emptyDir). fsGroup puts a team sticker on a shared drawer so the whole team may open it.

Where the app writesOwner and modeResult

🧓 Grown-up terms: fsGroup makes the kubelet set group ownership on supported volumes and adds that group to the process. Support depends on the volume type and CSI driver. fsGroupChangePolicy: OnRootMismatch avoids slow recursive changes on big volumes. A fresh PVC is often owned by root. supplementalGroups adds more groups. Kubernetes also merges the user's groups from the image's /etc/group. The supplementalGroupsPolicy: Strict option stops that implicit merge (a newer field, so check your cluster version). When runAsUser is set without runAsGroup, the primary group is usually 0. Rows 3 and 4 use an image that has a /app/cache folder owned by UID 1000 and the standard /tmp (mode 1777).

🕴️ Bouncers: seccomp, AppArmor and SELinux

Even a worker with the right badge and keycards still asks the building staff for things. Bouncers check the request itself.

🎯 Analogy. seccomp is a short list of the kinds of requests the staff will accept from your floor ("open a file", "send a message"; never "reboot the building"). AppArmor and SELinux are room-specific rules: "this team may read these folders and write only here".

🧓 Grown-up terms: a request must pass both checks. The RuntimeDefault profile (from containerd or CRI-O) blocks a few dozen dangerous or rarely needed syscalls and lets the rest through. Several of them are only allowed when the matching capability is held, which is why the table above works this way. The Kubernetes docs warn that default profiles can differ between runtimes and versions, and the custom profile here is only an illustration.

🏠 Private offices (user namespaces)

What if the manager's badge on your floor was only valid on your floor?

🎯 Analogy. Inside your private office, badge 0 really is the manager. But the building's records translate every number: your "badge 0" is recorded as an ordinary visitor number everywhere else. If someone sneaks out of your office, they are just a visitor.

Inside the container:
On the node: 
apiVersion: v1
kind: Pod
metadata:
  name: userns
spec:
  hostUsers: false          # a pod spec field, not part of securityContext
  containers:
  - name: app
    image: debian:trixie-slim
    command: ["sleep", "3600"]

🧓 Grown-up terms: user namespaces are stable since Kubernetes v1.36 (first available in v1.28) and you opt in per pod with hostUsers: false. Without a user namespace, root in a container is root on the node if it escapes. Capabilities granted to the container are then valid on the host too. With one, they are only valid inside the namespace. The mapping is shown by cat /proc/self/uid_map, where the last number should be 65536 inside the container.

🕵️ Building inspectors: Pod Security Standards

Inspectors check every pod before it moves in. Three rulebooks, from relaxed to strict.

🎯 Analogy. Privileged = "anything goes" (for the building's own maintenance crew only). Baseline = "no known dangerous tricks". Restricted = "follow every current best practice".

🟥 Privileged

No restrictions. For trusted system and infrastructure workloads.

🟨 Baseline

Blocks known privilege escalations: privileged containers, host namespaces, hostPath, added capabilities outside a short list, Unconfined seccomp.

🟩 Restricted

Everything in baseline plus: runAsNonRoot: true, allowPrivilegeEscalation: false, drop ALL capabilities (only NET_BIND_SERVICE may be added back), seccomp RuntimeDefault or Localhost, limited volume types.

🧓 Grown-up terms: Pod Security Admission (PSA) is the built-in controller that enforces these levels. It is generally available since v1.25 and replaced PodSecurityPolicy. You switch it on per namespace with labels. The baseline allowed list for capabilities.add is: AUDIT_WRITE, CHOWN, DAC_OVERRIDE, FOWNER, FSETID, KILL, MKNOD, NET_BIND_SERVICE, SETFCAP, SETGID, SETPCAP, SETUID, SYS_CHROOT. Notice that NET_RAW is not on it, even though many runtimes grant it by default.

🧪 Inspect a pod

Namespace labels

🧓 Grown-up terms: enforce rejects, audit adds an audit-log annotation and warn shows the user a warning. Enforcement works on the Pod that a controller creates, so a Deployment can be accepted while its pods are rejected (check ReplicaSet events). PSA is checked when pods are created or updated and does not evict running pods. Exemptions are configured in the API server and should be kept short.

🧰 When three levels are not enough: policy engines

PSA has just three fixed levels. For field-level rules, such as "every container must set runAsNonRoot" or "images only from our registry", add a policy engine.

ValidatingAdmissionPolicy

Built into the API server, written in CEL. Stable since v1.30.

Kyverno

Policies written as Kubernetes YAML. Can validate, mutate and generate.

OPA Gatekeeper

Policies written in Rego, with constraint templates.

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: require-run-as-non-root
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
    - apiGroups: [""]
      apiVersions: ["v1"]
      operations: ["CREATE", "UPDATE"]
      resources: ["pods"]
  validations:
  - expression: "object.spec.containers.all(c, has(c.securityContext) && has(c.securityContext.runAsNonRoot) && c.securityContext.runAsNonRoot == true)"
    message: "every container must set securityContext.runAsNonRoot: true"
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: require-run-as-non-root
spec:
  policyName: require-run-as-non-root
  validationActions: ["Warn"]      # switch to ["Deny"] once the warnings are clean
  matchResources:
    namespaceSelector:
      matchLabels:
        policy: restricted

This example only counts container-level settings. Test any policy on a non-production cluster first (kubectl apply --dry-run=server).

    📄 A hardened Deployment you can start from

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels: {app: web}
  template:
    metadata:
      labels: {app: web}
    spec:
      automountServiceAccountToken: false     # only if the app does not call the API
      # hostUsers: false                      # optional: needs nodes that support user namespaces
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        runAsGroup: 10001
        fsGroup: 10001
        seccompProfile:
          type: RuntimeDefault
      containers:
      - name: web
        image: registry.example.com/web:1.0.0   # prefer a pinned tag or digest
        ports:
        - containerPort: 8080
        securityContext:
          allowPrivilegeEscalation: false
          readOnlyRootFilesystem: true
          capabilities:
            drop: ["ALL"]
        volumeMounts:
        - {name: tmp, mountPath: /tmp}
      volumes:
      - name: tmp
        emptyDir: {}

    This passes the restricted level. Add resource requests and limits, probes and a NetworkPolicy for a complete setup.
